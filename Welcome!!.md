# Organizational paradigm
#### Using tags: a tool for building association
#tags are a feature which has a variety of behavior, but in its essence creates an association between notes as well as being an object that you can search for and manipulate[^1]

- **To search for tags**, navigate to the magnifying glass icon in the top left. Try typing out **tag:#plant** to search for all of the files that are relating to plants. The output should look something like this: 
  ![600](https://i.gyazo.com/6ec8891dfa54d34ed2e711072ae94479.png)

	This output gives where the tag is found, allowing you to jump to this tags location in the Anise, Tag List, Calendula, or the 37 other files in which this tag occurs. 
[^1]: Tag wrangler and tag pages are the plugins which can be used to manipulate tags seamlessly and with powerful results. Tag pages allows you to create a note which contains all instances of the mentioned tag in a running list that will update every time something in the vault is changed. A useful part of this can be observed in the [[TODO_Tags]] page, where all tasks are organized with their corresponding file linked for ease of access.

#### Using links
As you saw in the graph view, there are many other links between files that exist that are not directly mediated by a tag. All of these lines are because of [[links]]. Some links [[aren't highlighted]], meaning that they are pointing to no file. Links that do point to a file are bright, such as [[~Tag List]], [[01Action plans]], [[Anise]], and so on. Creating a link is easy! simply use two square brackets and sandwich your text in-between them, like so \[\[ \]\].  Alternatively, right click and select "**add link**" to create these square brackets for you. 
Example of what you should see when typing into the double square brackets:
![700](https://i.gyazo.com/54b3ca9ab4c4364a101094f5bc2f497d.png)

After that, simply type in the name of the file that you want to link to and *voila*! Now you have connected to notes together! The next challenge is to do so with meaning and intention. If practiced, this tool can make a map that can look semantically similar to the territory that we are trying to explore, which is how to garden sustainably. 

Some other behaviors to note about greyed out links. These files can be instantiated later, which can be more useful than one would expect when thinking about longer term learning projects. Essentially it's like having an empty folder in an infinite filing cabinet that you can jump to whenever you feel like it, and put something in there. 

For more on links, visit the [obsidian help site](https://help.obsidian.md/links).

#### Using the search bar syntax
There are certain prefixes to searches that can help parse down your criteria for what you are searching for. Without these, the search functionality is a complete mess, so before you type the keyword you want to search discern whether it is a file, tag, inline text, path, or property, or section that you are referring to
- **file:{your_TEXT_here}** --> "Search for a file name that contains or matches {your_TEXT_here}"
- **line:{your_TEXT_here}** --> "Search for a line in a file that contains or matches/containes {your_TEXT_here}"
- **tag:{your_TEXT_here}** --> "Search for a tag in the vault that contains or matches {your_TEXT_here}"
I rarely use the ones below
- **path:{your_TEXT_here}** --> "Search for a path name that contains or matches {your_TEXT_here}"
- **\[{your_TEXT_here}]** --> "Search for a property which contains or matches {your_TEXT_here}"
- **section:{your_TEXT_here}** --> "Search for a section (header) that contains or matches {your_TEXT_here}"

#editor ile:  and tag: are the main prefixes that I use, so they inform the organization of this vault in its current state the most.

#### Properties
You will notice that the templates have these blocks at the very top of them containing a key (on the left) and a value (on the right)

![800](https://i.gyazo.com/d1d8835d915b222246504cb9fd5c10bd.png)
These properties, at least for this specific template, are not so intimidating and don't need to be finagled with. The year, month_start, and month_day properties take on a value when the insert template function is used. Furthermore, the UsageNum and LastDateMod properties or for the engagement tracker immediately below the property list. Overall, the properties on this file are more for tracking dates and maybe writing in a blurb under the Specific_usage property. At least, these are my intentions with creating these. 

The importance of understanding this specific file is purely for the sake of being aware of how properties factor into the organization of the vault. For Action Notes, it is somewhat trivial. However, plant notes...

![800](https://i.gyazo.com/e70f058a09d7bf112e7a62ed3324c4ae.png)
... Are a lot! Their properties are tied into a table that tracks each property. In this way, from a higher view, we can organize plant notes on the scale of dozens or hundreds of notes using simple shared properties. This is a very useful tool whose power can be seen in the [[Plant YAML tables.base]] file. 

I'd highly recommend respecting the usage of these properties when you are creating your own plant entries as it will allow for greater organizational freedoms when you are using your notes to plan your garden. The connections between which plants will work well together depending on functional properties, priortizing human use cases, and ensuring that the layers of plants are not going to lead to too competitive of a garden for certain plantlings, will emerge *easier* if you use and fill out the plant note template properties as you study.
